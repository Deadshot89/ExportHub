# RC1014 Aufgaben – Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Das bestehende ExportHUB-Aufgabenmodul um stabile Identität, Fälligkeit, Priorität, Zuständigkeit/Vertretung, Wiederholung, automatische Erledigung, direkte Vorgangsöffnung, persönliche Erinnerungen und einen echten Browser-Funktions-/Designtest erweitern, ohne ein zweites Aufgaben- oder Persistenzsystem einzuführen.

**Architecture:** RC1014 ergänzt den vorhandenen `state.tasks`-Pfad durch einen isolierten, rein funktionalen Lifecycle-Kern und einen dünnen Runtime-Adapter. Die bestehende Aufgabenansicht, die fünf Gruppen, bestehende State-/Persistenzpfade und bestehende ExportHUB-Navigation bleiben autoritativ. Der gemeinsame RC1014-Build bindet Lifecycle, Runtime und CSS in Produktion, TESTSERVICE und Demo identisch ein; Android erhält nur die für persönliche Erinnerungen und Direktöffnung nötige Snapshot-/Benachrichtigungsintegration.

**Tech Stack:** Vanilla JavaScript, Node.js 24 / `node:test`, bestehender ExportHUB Canonical Runtime, Android Java 17 / Gradle, Playwright Chromium, GitHub Actions, Azure Static Web Apps.

**Spec:** `docs/superpowers/specs/2026-09-09-rc1014-tasks-final-design.md`

## Global Constraints

- Genau fünf fachliche Gruppen bleiben bestehen: `Offene Sendungen`, `Fehlende POD`, `Kunde angemeldet`, `Picks`, `Offene ABDs`.
- Kein zweites Aufgaben-, Rechte-, Diagnose- oder Persistenzsystem.
- `state.tasks` und die vorhandenen ExportHUB-Speicherpfade bleiben die autoritative Aufgabenquelle.
- Firmen- und Umgebungsisolation darf durch Aufgaben, URL, Header, Android oder Vertretung nie umgangen werden.
- Nicht berechtigte Bereiche bleiben unsichtbar; keine Schloss-/„Keine Berechtigung“-Kacheln.
- Erinnerungszeiten bleiben exakt 09:00, 12:00 und 15:00 Uhr.
- Produktion, TESTSERVICE, Demo und Android müssen auf demselben RC1014-Stand freigegeben werden.
- Bestehende RC1001/RC1002/RC1003/RC996-Aufgabenverträge bleiben Regressionen.
- Bestehende RC1013 Gate41-, QR-, Lieferavis- und Diagnosekorrekturen dürfen nicht zurückfallen.
- Browser-Visualtest muss Desktop 1440×900, Tablet 1024×768 und Smartphone 390×844 prüfen.
- Release erst nach frischem Main-Contract, gemeinsamem Drei-Umgebungen-Deploy, Live-Check und Android-Build.

- [ ] **Step 2: RED bestätigen**

Run: `node --test test/rc1014-task-lifecycle.test.mjs`
Expected: FAIL an den neuen Reconcile-Fällen.

- [ ] **Step 3: Gruppenbezogene Reconcile-Regeln implementieren**

Regeln:
- `Fehlende POD`: done nur bei fachlich vollständiger Abholung + gültigem POD.
- `Offene ABDs`: done nur wenn bestehende ABD-Regel erfüllt und ABD vorhanden; keine Aufgabe bei nicht ABD-pflichtig.
- `Picks`: Abschluss ausschließlich über konkrete Pick-Identität.
- `Offene Sendungen`: done bei abgeschlossen/archiviert, `cancelled` bei storniert.
- `Kunde angemeldet`: bestehende Abschlussbedingung nicht neu erfinden; Runtime übernimmt den bereits vorhandenen Completion-Status und ergänzt nur Lifecycle-Metadaten.

- [ ] **Step 4: Wiederkehrende Folgeinstanz integrieren**

Wenn eine erledigte Aufgabe `recurrence`/bestehende Serienfelder besitzt und für die nächste Periode keine `identityKey`-gleiche Instanz existiert, `nextOccurrence` genau einmal anhängen. Bestehende `recurringSeriesId|weeklySeriesId|seriesId` bleiben in der neuen Instanz erhalten.

- [ ] **Step 5: Vertretung integrieren**

Aktive Abwesenheiten aus vorhandenem ExportHUB-State an `resolveAssignee` übergeben; `originalAssignee` nie überschreiben, `effectiveAssignee` nur innerhalb derselben Firma anwenden.

- [ ] **Step 6: Persistenz nur bei tatsächlicher Änderung auslösen**

Runtime vergleicht vor/nach Reconcile über stabile Felder; nur bei `changed===true` wird der vorhandene Persistenzcallback ausgeführt. Reines Rendern darf keinen Save-Loop erzeugen.
